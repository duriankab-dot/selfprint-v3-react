### Deployment Payload

### Initial Payload

สิ่งที่ browser ต้องดาวน์โหลดเมื่อผู้ใช้เปิด Selfprint

### Runtime Cost

สิ่งที่ browser ต้อง execute / decode / render

# 4. ASSET POLICY

## ห้ามทำ

* ห้ามลด Asset แบบเหมา ๆ

* ห้าม preload Asset ทั้งระบบโดยไม่จำเป็น

* แยก Critical / Non-Critical Assets

25. BATCH EXECUTION & CONTEXT STABILITY (CRITICAL PROTOCOL)
หลักการ: "ทำหลายอย่างในรอบเดียว อย่าทำทีละอย่างแล้วเปิดรอบใหม่"

ห้ามปฏิบัติโดยเด็ดขาด:

ห้ามเปิดแชท/คอนเท็กซ์ใหม่ (New Chat) ทุกครั้งที่เจอปัญหาเล็กน้อย

ห้ามถามคำถามย่อยกลับไปกลับมาโดยไม่รวบรวมงาน (Turn-by-turn waste)

ห้ามส่งโค้ดทีละไฟล์ แล้วรอให้ตอบรับ ก่อนจะส่งไฟล์ถัดไป (ถ้าไม่จำเป็น)

ต้องปฏิบัติ:

รวบรวมงานทั้งหมดที่อยู่ในขอบเขตเดียวกัน (Feature/Phase) มาไว้ใน Batch เดียว

ถ้าต้องแก้ไขหลายไฟล์ (เช่น Component + Hook + Test + Style) ให้ส่ง Pull Request (PR) เสมือน ที่แก้ครบทุกไฟล์ในรอบเดียว

ถ้าโค้ดชุดใหญ่เกินจะล้น Context ให้แจ้งสรุป "งานเสร็จใน Batch นี้" และสร้าง Hand-off Document สั้น ๆ (สิ่งที่ทำ, สิ่งที่ค้าง, สิ่งที่ต้องต่อ) ก่อนจะขึ้นรอบใหม่ เพื่อให้รอบใหม่ไม่ต้องเริ่มจากศูนย์

เหตุผล: การเปิด Context ใหม่บ่อยๆ ทำให้ AI สูญเสียความเข้าใจเชิงลึก (Deep Context) ของโปรเจกต์ ส่งผลให้โค้ดที่เขียนขาดความสอดคล้องกับโครงสร้างเดิม และเสียเวลาอ่านซ้ำ (Re-read) สิ่งที่เคยทำไปแล้ว

26. PHASE COMPLETION & DOCUMENTATION PROTOCOL
หลังจากที่ทำงานในแต่ละ Phase / Feature / Epic เสร็จสมบูรณ์ (เช่น สร้างระบบ Auth, สร้างระบบ Fingerprint Capture, ปรับโครงสร้าง Lazy Loading) ต้องทำตามนี้ทุกครั้ง:

1. อัปเดตเอกสารที่เกี่ยวข้อง (Documentation Update):

ถ้ามีไฟล์ README.md → อัปเดตคำอธิบายฟีเจอร์ที่เพิ่ม / วิธีรัน / ตัวแปร Environment ใหม่

ถ้ามีไฟล์ docs/architecture.md หรือ docs/performance.md → อัปเดต Diagram หรืออธิบาย Load Strategy ที่เปลี่ยนไป

ถ้าไม่มีไฟล์เอกสารในโปรเจกต์ → ให้สร้างไฟล์ docs/PHASE_SUMMARY_<ชื่อเฟส>.md เพื่อบันทึกสิ่งที่ทำไว้สำหรับอ้างอิงในอนาคต หรือสำหรับสมาชิกทีมคนอื่น

2. สรุปผลลัพธ์ให้ฉัน (User):

สรุปสั้น ๆ ว่า "Phase นี้ทำอะไรไปบ้าง" (Bullet Points)

แจ้งขนาด Bundle ที่เปลี่ยนแปลง (ก่อน-หลัง ถ้าวัดได้) หรือ Performance Impact โดยสังเขป

แจ้งงานค้าง (ถ้ามี) และ Plan สำหรับ Phase ถัดไป

ห้ามข้ามขั้นตอนนี้เด็ดขาด เพราะเอกสารคือ "ความทรงจำระยะยาว" ของโปรเจกต์ ช่วยลดการทำงานซ้ำและทำให้การพัฒนาเป็นระบบมากขึ้น

27. 100% VERIFICATION MANDATE (NON-NEGOTIABLE)
นี่คือกฎที่สำคัญที่สุดและถูกบังคับใช้เหนือกฎอื่นทั้งหมด:

“ทุกอย่างที่ทำ ต้อง Verify 100% ห้ามส่งมอบแค่ Implementation”

การ Verify หมายถึงขั้นตอนต่อไปนี้ ต้องทำครบทุกข้อ ก่อนจะบอกว่างานเสร็จ:

1. Static Analysis (Type Checking & Linting):

ตรวจสอบว่า TypeScript (หรือภาษาเป้าหมาย) ไม่มี Error

ตรวจสอบ ESLint / Prettier ผ่าน (ถ้ามี)

ห้ามส่งโค้ดที่มี any (TypeScript) โดยไม่มีเหตุผล หรือมี Warning ค้าง

2. Unit Test Execution (ตาม TDD):

ถ้าเขียน Logic สำคัญ → ต้องเขียน Unit Test ควบคู่ และยืนยันว่า Test ผ่าน (Pass)

ถ้าทำงานที่แก้ไขโค้ดเก่า → ต้องรัน Test Suite เดิมเพื่อยืนยันว่า ไม่ทำให้อะไรพัง (Regression)

3. Logic & Edge Case Review (Mental Walkthrough):

อธิบายให้ฉันฟังสั้นๆ ว่า Logic ทำงานยังไงในกรณีที่ (1) สำเร็จ, (2) ล้มเหลว, (3) มีข้อมูลน้อย, (4) Network ช้า

ยืนยันว่ามีการจัดการ Error + Fallback (ตามข้อ 18) ครบ

4. Build Simulation (ถ้าเป็น Frontend/Next.js):

จำลองการ Build (เช่น next build) เพื่อเช็คว่าไม่มี Error ระหว่าง Compile

เช็คว่า Dynamic Import ทำงานถูกต้อง (ไม่มี Reference Error)

5. Performance Rule Cross-check (ข้อ 22):

ทบทวนโค้ดที่เขียนด้วยคำถาม 8 ข้อในข้อ 22 (Q1-Q8) อีกครั้ง เพื่อยืนยันว่าไม่ละเมิดหลัก Performance

เงื่อนไข:

หาก Verify ข้อใดข้อหนึ่งไม่ผ่าน → ห้ามส่งโค้ดให้ฉัน ให้แก้ไขจนผ่านก่อน

หากไม่สามารถ Verify ได้ด้วยตัวเอง (เช่น ไม่มี Environment) → ให้แจ้งฉันว่า "ส่วนนี้ต้องพึ่งพา Environment จริง กรุณาช่วย Verify ตรง X ด้วย"

ห้ามใช้คำว่า "เดี๋ยวแก้ทีหลัง", "ไว้ Refactor ทีหลัง", หรือ "น่าจะใช้ได้" ทุกอย่างต้องพิสูจน์ได้ ณ เวลาส่งมอบ

28. AI EXECUTION HYGIENE & CODE CLEANUP
เพื่อให้การทำงานร่วมกันยาวนานและมีประสิทธิภาพ ให้ปฏิบัติตามกฎสุขอนามัยของโค้ดต่อไปนี้:

Dead Code Elimination: หากพบโค้ดที่ไม่ได้ถูกเรียกใช้ (Unused Import, Unused Function, Unused Variable) ให้ลบออกทันที อย่าเก็บไว้ "เผื่อใช้ทีหลัง"

Duplicate Consolidation: หากพบฟังก์ชันหรือ Logic ที่ทำงานเหมือนกัน (Duplication) ให้รวมเข้าเป็น Utility / Helper เดียวทันที (DRY Principle)

Mock/Placeholder Ban: ห้ามสร้าง Mockup, Placeholder, หรือ Hard-code Data ที่ไม่มีอยู่จริงเพื่อรอให้แก้ทีหลัง ทุกอย่างต้อง Implement จริง 100% หากต้องพึ่งพา API จริงที่ยังไม่พร้อม ให้ใช้ Fallback หรือ Interface ที่เป็นรูปธรรม

Post-Cleanup: หลังจากทำงานในแต่ละ Batch เสร็จ ให้ทำการจัดรูปแบบโค้ด (Formatting), ลบ Comment ที่ไม่จำเป็น (โดยเฉพาะ Code ที่ถูก Comment ทิ้งไว้), และจัดลำดับ Import ให้สวยงาม
